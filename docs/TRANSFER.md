# نقل البيانات إلى قاعدة العميل

## ماذا يفعل الزر
في اللوحة ← «نقل البيانات» (`/dashboard/transfer`، لصاحب المتجر وحده): يلصق العميل رابط قاعدة Neon فارغة أنشأها في حسابه، فيجري:
1. التحقق من الرابط (PostgreSQL على Neon فقط، اتصال مشفّر، بلا مضيفات خاصة) وأن القاعدة فارغة.
2. إنشاء الجداول بتطبيق migrations مشروع العميل ذرياً (آمن للإعادة).
3. نسخ كل بيانات المتجر بالترتيب وبدفعات (تصنيفات، منتجات، تركيبات، عملاء، شحن، خصومات، طلبات وبنودها ومدفوعاتها، تقييمات، سلات، تنبيهات، أسئلة، مرتجعات، تحليلات) مع التاجر والمتجر وتصميمه. أسرار المتجر لا تُنسخ.
4. مزامنة نهائية مع إيقاف قبول الطلبات لحظات، ثم مطابقة عدد صفوف كل جدول.
5. تحويل التوجيه ذرياً: يُسجَّل الرابط مشفّراً (AES-GCM بمفتاح مشتق من AUTH_SECRET) في `store_databases`، فيقرأ المتجر ويكتب في قاعدة العميل عبر `getTenantDb`.

الواجهة تعرض التقدم بالعربية وتتابع الخطوات تلقائياً، وتستأنف عند إعادة فتح الصفحة.

## بعد النقل
- نسخة المنصة لا تُستخدم، وتُحذف صفوفها بعد 7 أيام (`PLATFORM_COPY_DAYS`) عبر `ops/sweep`. الصور لا تُحذف.
- الرجوع «لقاعدة المنصة» لمدير المنصة وحده خلال المهلة (`rollbackTransferAction`): ينسخ البيانات عكسياً (ما أُضيف في قاعدة العميل يعود) ثم يحذف التوجيه. المتابعة بـ `stepRollbackAction`.

## حالات الفشل
- رابط خاطئ أو قاعدة غير فارغة: رسالة فورية ولا يتغير شيء.
- انقطاع أثناء النسخ: «إعادة المحاولة من حيث توقف» (النسخ upsert فلا تكرار)، وتعود حالة قبول الطلبات.
- عدم تطابق الأعداد: لا يُحوَّل التوجيه، وتُعاد المحاولة.
- تعذر فك تشفير الرابط (تغيّر AUTH_SECRET): يفشل المتجر بخطأ واضح ولا يرجع صامتاً لنسخة قديمة.
- الرابط لا يُسجَّل في أي سجل، وتُنقّى رسائل الأخطاء منه.

## قاعدة مستقلة لكل متجر (اختياري)
`NEON_API_KEY` و`NEON_PROJECT_ID` وعلم `store_db.per_store` في /admin/flags (مطفأ افتراضياً؛ غيابه = مطفأ). ينشئ فرعاً للمتجر ثم يمر بالمسار نفسه (`provisionStoreDbAction`). خطة Neon المجانية تحدّ الفروع، فهو للخطة المدفوعة.

## للمالك
بعد `npm run db:migrate` (0019) يعمل كل شيء. عند تغيّر مخطط جداول المتجر أعيدوا `npm run transfer:embed` (يفشل اختبار transfer إن نُسي).
